## Overview

Batch pipeline yang membaca PDF kontrak karyawan dari berbagai vendor (native, scan, hybrid) dan mengeluarkan nama karyawan, masa kontrak, dan status tanda tangan karyawan (signed/unsigned/uncertain), dengan keputusan auto-pass atau review untuk HR. Halaman berisi gaji tidak pernah keluar dari mesin lokal; satu-satunya data yang keluar adalah teks halaman identitas yang sudah di-mask, dikirim ke LLM cloud. Spesifikasi lengkap ada di `PRD & RFC Ekstraksi Kontrak Karyawan dari PDF.md`.

Website lokal (v1, uji coba): HR memilih satu atau beberapa folder kontrak di bawah satu folder root (untuk uji: folder OneDrive berisi kontrak sintetis), menjalankan OCR, lalu melihat hasil per file. Satu alur baca untuk "Jalankan OCR" (keputusan owner 2026-11-03, diubah 2026-11-11): pembacaan lokal adalah alur utama dan Claude hanya cadangan. Nama, periode, dan vendor dicocokkan lokal dengan nama file dan nama folder, posisi dibaca kedua mesin OCR lokal; teks halaman identitas ter-mask dikirim ke Claude hanya bila nama, periode, posisi, atau vendor masih ragu, dan jawabannya dipakai untuk kolom itu saja; potongan gambar baris NIK bila NIK lokal ragu, dan potongan area tanda tangan untuk setiap scan dan foto (PDF teks bila ragu) (tidak pernah satu halaman utuh). ENTITAS selalu dari nama file. Lewat Claude API bila `ANTHROPIC_API_KEY` diisi, selain itu lewat login Claude Code untuk uji lokal; `CLAUDE_MODE=off` membuat tidak ada yang keluar dari laptop.

Website meminta masuk lebih dulu (2026-11-05): login tiruan dengan email kantor dan nama, tanpa kata sandi, sebagai pengganti sementara Apps Gateway (SSO kantor). Email yang pertama kali masuk dicatat di tabel `User` (Drizzle + PostgreSQL; desainnya di ERD `../Database Design/Contract OCR ERD.vpp`). Sejak 2026-11-16 (permintaan mentor) ada dua peran, Reviewer dan Admin: pengguna baru adalah Reviewer nonaktif yang hanya melihat halaman "Menunggu aktivasi admin" sampai admin mengaktifkannya di halaman User (lihat Key Decisions); login terakhir dicatat setiap masuk. Sejak 2026-11-05 tiap Jalankan OCR juga disimpan ke database: satu baris `OCRHeader` per proses dan satu baris `OCRContractDetail` per PDF (lihat Key Decisions). Sejak 2026-11-06 banyak user bisa menjalankan OCR bersamaan: proses antre dan dibaca satu per satu dengan semua worker, PDF yang juga ada di proses sebelumnya dalam antrean tidak dibaca ulang tetapi hasilnya diambil, dan riwayat semua proses (siapa, kapan, hasilnya) terlihat oleh semua user.

Database: Drizzle + PostgreSQL (allowedStack). - Pengguna dan peran (permintaan mentor 2026-11-16; default berikut diusulkan agent dan dilaporkan ke owner): dua peran, Reviewer (semua fitur kecuali halaman User) dan Admin (ditambah halaman User). Pengguna baru Reviewer nonaktif. Pengguna nonaktif tetap mendapat sesi tetapi API menolak semua route selain `/api/auth/*` (403 `account_inactive`), dan halaman hanya menampilkan "Menunggu aktivasi admin"; status dibaca dari database di setiap request, jadi menonaktifkan langsung memutus sesi yang terbuka (proses OCR miliknya yang sedang berjalan tetap selesai). Admin pertama lewat `ADMIN_EMAILS` (env, Vault di production) dan bukan seed sekali jalan, karena di AIVA tidak ada shell untuk menjalankan perintah; email di daftar itu dijadikan Admin aktif setiap masuk, sehingga admin yang terkunci bisa kembali, dan halaman User tidak bisa mengubahnya (409 `admin_from_config`, karena perubahan itu akan dibatalkan saat masuk berikutnya). Admin tidak bisa mengubah peran maupun status dirinya sendiri (403 `cannot_change_self`). Migrasi `0004` menjadikan pengguna lama Reviewer nonaktif (least privilege; owner masuk lagi lewat `ADMIN_EMAILS`), dengan `lastLoginAt` kosong, bukan disalin dari `createdAt`, karena login terakhir mereka tidak diketahui. Pengguna benchmark `accuracy-check@example.com` tidak dijadikan admin: admin mengaktifkannya sekali sebagai Reviewer, dan `compare_accuracy.py` berhenti dengan petunjuk itu bila masih nonaktif. Penyebab gagal adalah kode pertama di `reasons` (tidak ada kolom errorCode); `checks` hanya catatan per kolom dari nilai yang terbaca, jadi kosong untuk file gagal dan dibatalkan. File yang sama di proses lain mendapat baris baru (documentKey diindeks, tidak unik); coba lagi di proses yang sama memperbarui baris. Kolom bebas panjang (`folders`, `checks`, `reasons`) varchar tanpa batas, karena `folders` di uji 800 file sudah 3.905 karakter; nilai lain dipotong ke panjang kolom, tanggal hanya ISO, NIK hanya bila 16 digit. Penyimpanan tidak pernah menghentikan OCR: bila gagal, halaman hasil memberi peringatan dan log hanya membawa id job dan kode error (pesan error database bisa memuat nilai baris). NIK lengkap dan nama tersimpan plaintext: hanya boleh di laptop dengan kontrak sintetis (lihat PROJECT.md, Saved OCR results).

Kegagalan bukan bacaan: PDF yang gagal lagi tetap menjadi baris kosong dan kuning dengan alasannya.

Hasil per PDF hanya diambil dari proses yang masih antre atau berjalan saat proses baru dimulai, dan hanya bila cara bacanya sama (OCR atau Tanpa OCR); hasil proses yang sudah selesai tidak dipakai ulang. Proses yang ditunggu gagal atau dibatalkan untuk PDF itu → proses berikutnya membaca sendiri (atau menunggu proses lain di depannya yang juga memuatnya). Semua user melihat semua proses dan hasilnya (riwayat dari database; proses lama dibuka sebagai halaman hasil utuh dari JSON `result`). Default agent yang disebut ke owner: hanya yang menjalankan boleh batal dan coba lagi (`403 not_your_job`); proses antre/berjalan saat backend berhenti ditandai `interrupted` saat start berikutnya; total token proses hanya dari PDF yang dibacanya sendiri (hasil yang diambil dihitung di proses asalnya), sehingga token tidak terhitung dua kali.
